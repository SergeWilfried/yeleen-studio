Studio production architecture

How the current mock becomes a live product on fal.ai, Cloudflare and Railway for about $10 a month in fixed cost. The browser keeps the same job states, balance and refunds it has today. Only the engine behind them changes.

Prepared 14 Oct 2026Scope: image, video, audio, Spot pub, library, brand kitAssumes 1–2 developers

How a generation moves through the system

The browser never talks to fal. Every paid action goes through one Worker, and only one Durable Object per account can change the jeton balance. Select a step to see which parts it touches.

Money and guardrails

Pricing and the ledger

  • Jeton price stays near 33 FCFA. Each model costs fal's price times two, with a floor, from one catalog file the app and the Worker both import.
  • Every debit, refund and top-up is a ledger line. A daily job compares the ledger to fal's invoice so margin is measured, not assumed.
  • Refunds and payment credits are idempotent per job or payment id, so a retried webhook cannot pay twice.

Protect the budget

  • A small free credit that needs a verified phone number. Anything looser is the first abuse.
  • Per-account concurrency (the current limit of two) and a daily jeton cap.
  • A global monthly fal budget with a kill switch on the Worker.
  • Prompt moderation before the debit, so a refusal costs nothing.
  • The fal key lives only in Worker secrets.

Ten weeks to a public pilot with one or two developers. Each phase swaps one piece of the mock for the real thing behind the same interface, so the app keeps working throughout.

0 · Foundations

Week 1
  • Workers and Pages deployed from the repo.
  • Shared catalog package for models and prices.
  • D1 schema for accounts, jobs, assets, ledger.
  • fal key in Worker secrets.

Done when the app loads from Pages and calls a health route on the Worker.

1 · Wallet and images

Weeks 2–3
  • Wallet Durable Object with debit, refund and a ledger.
  • POST /jobs, fal image submit and webhook.
  • Copy outputs to R2, WebSocket status.
  • Replace the mock submit behind the same interface.

Done when an image generates, a forced failure refunds, and the ledger reconciles.

2 · Video, audio, library

Weeks 4–5
  • Video and voice models from the same catalog.
  • Library read from D1 and R2, uploads to R2.
  • Send-to and chain references use stored files.

Done when the library shows the same assets on two devices.

3 · Spot and montage

Weeks 6–7
  • Spot run moves to the server, with the same stages and retries.
  • Queue and Railway ffmpeg worker from the manifest.
  • Brand kit stored per account, logo in R2.

Done when a spot finishes after the tab is closed.

4 · Accounts and money

Weeks 8–9
  • WhatsApp OTP and Google sign-in.
  • Mobile Money top-up and payment webhook.
  • Free credit with phone check, spend caps, budget kill switch.

Done when a stranger can sign up, top up and generate without help.

5 · Pilot

Week 10 onward
  • Invite around twenty studios.
  • Track margin per jeton from the ledger.
  • Then fal workflows for chains and a WhatsApp entry point.

Done when margin per jeton holds across a week of real use.

Decide and start now

Where should a Spot run live in the first release?

On the server RecommendedA spot survives a closed tab, can be retried by support and reads cleanly in the ledger. More work in phase 3.
In the browser for the pilotReuses today's orchestration and ships sooner. A closed tab loses the run, and the server cannot see the stages.

Long lead items to start in week 1

  • Merchant account and KYC with a Mobile Money aggregator.
  • WhatsApp Business sender and OTP template approval.
  • fal account limits and billing set up for the expected volume.

Main risks and the response

  • fal cost spike: daily ledger-to-invoice check and the budget kill switch.
  • Forged callbacks: signed webhook URLs and signature checks.
  • Expiring fal links: copy to R2 before marking a job done.
  • Montage backlog: queue depth alert, scale Railway to two instances.
